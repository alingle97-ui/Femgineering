Routes for Topics

Lesson 2 · Femgineering Dashboard

Lesson 1 gave you two routes that each return one fixed string — you typed the whole page by hand. The real Topics section needs to show a *list* of topics (Menopause, Endometriosis, PCOS, however many you add), and right now you don't have a database yet — that's coming in a later lesson. This lesson bridges the gap: store your topics as plain Python data, right inside app.py, and write one route that turns that data into HTML automatically — instead of writing a new line of HTML for every topic by hand.

Quick refresher — lists and dictionaries

You'll be rusty on these from college, so a quick refresher before using them:

A list is an ordered collection, written with square brackets:

colors = ["red", "green", "blue"]

A dictionary (dict) stores named fields, written with curly braces and key: value pairs — like a single record with labeled fields:

topic = {"name": "Menopause", "why_it_matters": "Still under-researched and often dismissed by clinicians."}

You access a dict's value by its key: topic["name"] gives you "Menopause".

Put those together and a list of dicts is a stand-in for a table of records — one dict per row, one key per column. That's exactly how we'll represent your topics before a real database exists.

Step 1 — Add the topics data

In app.py, above your routes, add:

topics = [
    {"name": "Menopause", "why_it_matters": "Still under-researched and often dismissed by clinicians."},
    {"name": "Endometriosis", "why_it_matters": "Takes years to diagnose despite affecting 1 in 10 women."},
]

This mirrors the Name and Why it matters fields from the Topics section of the PRD. It's just sitting in memory as a Python variable right now — nothing is saved anywhere, so it resets every time the server restarts. That's fine for this lesson; persisting it for real is what the database lesson will solve.

Step 2 — Write a route that loops over it

@app.route("/topics")
def topics_page():
    html = "<h1>Topics</h1>"
    for topic in topics:
        html += f"<h2>{topic['name']}</h2><p>{topic['why_it_matters']}</p>"
    return html

New pieces here, one at a time:

  • def topics_page(): — the function name just needs to be unique in the file (same rule as Lesson 1). It doesn't have to match the URL /topics, though naming it similarly makes the code easier to read.
  • html = "<h1>Topics</h1>" — a variable holding a string we're going to build onto piece by piece, starting with a page heading.
  • for topic in topics: — a for loop: run the indented lines below once for every item in the topics list, with topic holding the current dict each time through.
  • html += f"..." — += means "add this onto the end of html," so each loop pass appends another topic's HTML instead of overwriting the last one.
  • f"...{topic['name']}..." — an f-string (the f before the quotes matters). Anything inside { } gets evaluated as Python and dropped into the string — so {topic['name']} pulls that dict's actual name into the HTML.
  • return html — sits after the loop (not indented inside it), so it runs once, after all topics have been appended, returning the complete page.

Step 3 — Run it

If your server's still running with debug=True, just save and visit http://127.0.0.1:5000/topics. Otherwise, python3 app.py first.

Win: a page listing both topics, with their headings and descriptions — generated from Python data, not typed into HTML by hand.

Try it yourself

Before moving on, without looking back at Step 1:

  1. Add a third dict to the topics list — pick a real topic you'd want to cover, with your own name and why_it_matters.
  2. Reload http://127.0.0.1:5000/topics and confirm it shows up — without adding a single new line of HTML.

If it doesn't show up, check the punctuation first — a missing comma between dicts in the list is the single most common thing to trip over here.
