A Real Database for Topics

Lesson 4 · Femgineering Dashboard

Back in Lesson 2, your topics list was a warning waiting to happen: it lives only in your computer's memory while the server is running. Stop the server, and it's gone — you'd have to retype your topics into the code every single time. That's fine for a lesson, useless for a real tool. This lesson replaces that list with a SQLite database — an actual file on disk that remembers your topics permanently, restart or not.

What SQLite is

A database is just a place to store data permanently and query it back out. There are heavier database systems (Postgres, MySQL) that run as a separate always-on program you'd have to install and start up. SQLite is different — the whole database is a single file sitting in your project folder, and Python already knows how to talk to it via a built-in module called sqlite3. No pip install needed this time, unlike Flask — it comes with Python itself.

To talk to it, you write SQL (Structured Query Language) — a small language of its own, separate from Python, built specifically for describing tables and asking questions of them. You'll only need three SQL commands today: CREATE TABLE, INSERT INTO, and SELECT.

Step 1 — Write a setup script

Create a new file, init_db.py, in the Femgineering folder (next to app.py, not inside templates):

import sqlite3

connection = sqlite3.connect("femgineering.db")

connection.execute("""
    CREATE TABLE IF NOT EXISTS topics (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        name TEXT NOT NULL,
        why_it_matters TEXT NOT NULL
    )
""")

connection.execute("DELETE FROM topics")

connection.execute(
    "INSERT INTO topics (name, why_it_matters) VALUES (?, ?)",
    ("Menopause", "Still under-researched and often dismissed by clinicians."),
)
connection.execute(
    "INSERT INTO topics (name, why_it_matters) VALUES (?, ?)",
    ("Endometriosis", "Takes years to diagnose despite affecting 1 in 10 women."),
)

connection.commit()
connection.close()

print("Database ready.")

New pieces, one at a time:

  • sqlite3.connect("femgineering.db") — opens that file if it exists, or creates it if it doesn't. This one call is basically "give me a handle to my database."
  • connection.execute("""...""") — runs a string of SQL against the database. The triple-quotes (""") let the string span multiple lines, which is just for readability here.
  • CREATE TABLE IF NOT EXISTS topics (...) — defines a table named topics, with three columns: id, name, why_it_matters. This is the persistent version of the shape your list-of-dicts already had — name and why_it_matters are the same fields from Lesson 2; id is new.
  • id INTEGER PRIMARY KEY AUTOINCREMENT — gives every row a unique number automatically (1, 2, 3, ...), so you always have a reliable way to refer to "that one specific topic" later, even if two topics end up with the same name.
  • TEXT NOT NULL — this column holds text, and it's required (a row can't be saved without it).
  • IF NOT EXISTS — makes it safe to run this script more than once; it won't complain that the table is already there.
  • DELETE FROM topics — empties the table before reinserting, so re-running this script doesn't leave you with duplicate topics every time.
  • INSERT INTO topics (name, why_it_matters) VALUES (?, ?), with ("Menopause", "...") passed as a second argument — the ? placeholders get safely filled in with those values. Always do it this way (never by building the SQL string yourself with + or an f-string) — placeholders protect you from a real security problem called SQL injection, where someone's typed-in text could otherwise be interpreted as a database command instead of plain data.
  • connection.commit() — SQLite doesn't permanently save your changes until you explicitly commit them. Forgetting this is a classic "why didn't my data save" bug.
  • connection.close() — releases the file so nothing's left dangling open.

Step 2 — Run it once

python3 init_db.py

You should see Database ready. print out, and a new file, femgineering.db, appear in your folder. Unlike app.py, this script isn't something that runs continuously — it's a one-time (or "run it whenever I want to reset my data") setup step.

Step 3 — Read from the database instead of the list

In app.py, remove the hardcoded topics = [...] list from Lesson 2 entirely, add import sqlite3 at the top, and rewrite the route:

import sqlite3
from flask import Flask, render_template

app = Flask(__name__)

@app.route("/topics")
def topics_page():
    connection = sqlite3.connect("femgineering.db")
    connection.row_factory = sqlite3.Row
    topics = connection.execute("SELECT * FROM topics").fetchall()
    connection.close()
    return render_template("topics.html", topics=topics)

New pieces:

  • The connection now opens inside the route, not once at the top of the file. This is standard practice: a web app can get many requests at once, so each request grabs its own fresh connection and closes it when done, rather than sharing one connection for the whole app's lifetime.
  • connection.row_factory = sqlite3.Row — without this line, each row comes back as a plain tuple like (1, "Menopause", "..."), and you'd have to remember that position 1 means "name." This line makes each row behave like a dict instead, so topic.name and topic.why_it_matters — the exact same dot notation your template already uses — keep working with zero changes to topics.html.
  • SELECT * FROM topics — the SQL question "give me every column, for every row, in the topics table." * means "all columns."
  • .fetchall() — actually pulls the matching rows back as a list, which is what makes topics here loop-able in the template exactly like the hardcoded list from Lesson 2 did.

Step 4 — Run it and prove it persists

Restart your server (python3 app.py) and visit http://127.0.0.1:5000/topics — same page as before. Now stop the server entirely (Ctrl+C), and start it again. Reload the page.

Win: your topics are still there after a full restart — because they now live in femgineering.db on disk, not in a Python variable that resets every time the program starts.

Try it yourself

Before moving on, without looking back at Step 1:

  1. Add one more INSERT INTO topics (...) statement to init_db.py, for a real topic of your choosing.
  2. Run python3 init_db.py again, then reload /topics and confirm your new topic shows up.

Notice you're editing init_db.py, not app.py or the template — the route and the template don't care how many topics exist or where they came from; they just display whatever the database hands back.
